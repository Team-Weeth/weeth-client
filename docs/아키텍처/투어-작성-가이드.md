# 투어(스포트라이트 코치마크) 작성 가이드

AI가 읽는 기계 판독 스펙은 `.claude/rules/tour.md`에 있다. 이 문서는 기획·디자인이 실제로 묻는 질문에 답한다. 레포가 이미 이 분리를 쓰고 있다 — [[api-타입-사용법]], [[bundle-analyzer-사용법]]도 `.claude/rules/*`와 나란히 존재한다.

## 투어 vs 모달 튜토리얼, 언제 뭘 쓰나

| 상황 | 선택 |
| --- | --- |
| 화면 안의 특정 버튼/필드/컬럼 하나를 처음 쓰는 사람에게 짧게 알려주고 싶다 | **투어** |
| 여러 화면에 걸친 전체 흐름을 설명해야 한다 (예: 첫 로그인 시 앱 전체 둘러보기) | 모달 튜토리얼 (`HomeTutorialDialog` 같은 캐러셀) |
| 특정 작업 영역 전체("이 섹션 전체가 새로워요")를 강조하고 싶다 | 영역 오버레이 (`DuesOnboardingOverlay` 같은) |
| 플래그로 숨겨진 기능이 켜졌을 때 "여기 생겼어요"를 알려주고 싶다 | **투어** (가장 흔한 케이스) |

이미 있는 두 온보딩(모달 튜토리얼, 영역 오버레이)을 투어로 바꾸지 않는다. 셋은 역할이 다르다.

## 스텝 수와 문구 톤

- **스텝 2~3개 이내.** 그 이상이면 모달 튜토리얼 쪽이 맞는 상황일 가능성이 높다.
- **각 스텝 본문은 2줄 이내.** 모바일 화면에서 툴팁이 화면의 절반을 가리면 안 된다.
- 톤: "~할 수 있어요", "~해보세요" 같은 가벼운 안내체. 경고나 강제처럼 읽히지 않게.
- 제목은 기능명이 아니라 **사용자가 얻는 결과**로 쓴다. 예: "경고 기능이 추가되었습니다"(X) → "경고를 따로 기록할 수 있어요"(O)

## 모바일에서 어떻게 보이는지

Weeth 사용자 다수가 모바일이다. 투어 툴팁은 화면 폭에서 32px를 뺀 너비로 줄어들고(`min(320px, 100vw - 32px)`), 타깃 주변 공간에 따라 위/아래로 자동으로 뒤집힌다. 디자인 리뷰 시 데스크톱 화면만 보고 승인하지 않는다 — 실제 기기 폭(360px 기준)에서 확인한다.

## 문구를 나중에 고치면

투어 정의에는 `version` 번호가 있다. **문구나 스텝 구성을 바꿀 때는 반드시 버전을 올린다.** 그러면 이미 그 투어를 본 사용자에게도 새 버전이 다시 노출된다. 버전을 안 올리면 바뀐 내용이 조용히 묵힌다 — 새 사용자만 보고 기존 사용자는 영원히 못 본다.

## 지표는 어디서 보나

PostHog에서 아래 이벤트로 퍼널을 본다:

- `tour_started` → `tour_step_viewed` → `tour_completed` 또는 `tour_skipped`
- `tour_step_failed` — 이게 쌓이면 코드 리팩터링 중 타깃 요소가 지워졌다는 뜻. 알게 되면 즉시 개발팀에 공유.

투어별 완료율이 낮으면(예: 1스텝에서 대부분 skip) 문구나 타이밍(`startDelayMs`)을 먼저 의심한다.

## 요청 흐름

1. 어떤 기능을, 어떤 화면에서, 누구에게(역할/플래그) 알릴지 정리해서 개발팀에 전달
2. 개발팀이 `/feature-tour`로 초안을 만들면 스텝별 제목/본문 승인 요청이 온다 — 거기서 문구를 확정
3. 배포 후 1~2주 뒤 PostHog 퍼널로 효과 확인
