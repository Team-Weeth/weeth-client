## 문제

Step2(납부 대상)에서 새로고침하면 "전체 0 / 선택됨 4 / 제외됨 -4 / 멤버가 없습니다"가 뜨며 목록이 사라짐.

- **원인:** `accountId`(초안 식별자)는 [`useDuesSetupStore`](../../src/stores/useDuesSetupStore.ts)에서 **의도적으로 메모리 전용**(`partialize` 제외 + `merge`에서 항상 `null`). 새로고침하면 `accountId = null`.
- `accountId`를 다시 확보하는 `createDraft` 호출은 **Step1에만** 존재([`DuesSetupStep1.tsx`](../../src/components/admin/dues/setup/DuesSetupStep1.tsx))했고, Step2~5는 "Step1을 거쳐 왔다"고 가정.
- Step2에서 직접 새로고침 → `accountId = null` → [`useDuesPaymentTargetsQuery`](../../src/hooks/queries/admin/useDuesSetupQueries.ts)가 `skipToken`으로 요청을 건너뜀 → `allTargets = []` (전체 0). 반면 `selectedMemberIds`는 persist돼 살아있어 선택됨 4, 제외됨 = 0 − 4 = **−4**.
- 즉 "데이터가 날아간 것"이 아니라 **accountId를 잃어 목록을 다시 못 불러오는 것.** `commitStep`도 `accountId === null`이라 저장·다음 진행 불가.

## 수정

- **신규 훅:** [`useEnsureDuesAccountId`](../../src/hooks/admin/useEnsureDuesAccountId.ts) — `accountId`가 `null`이고 persist된 `cardinalNumber`가 있으면 `createDraft`를 재호출해 accountId를 복구. 기존 초안이 있으면 서버가 동일 accountId를 `isNew=false`로 반환하므로 안전.
- **적용:** [`DuesSetupStep2`](../../src/components/admin/dues/setup/DuesSetupStep2.tsx) / [`Step3`](../../src/components/admin/dues/setup/DuesSetupStep3.tsx) / [`Step4`](../../src/components/admin/dues/setup/DuesSetupStep4.tsx) / [`Step5`](../../src/components/admin/dues/setup/DuesSetupStep5.tsx)에서 마운트 시 호출.
- Step1은 "이어서 작성" alert 등 자체 복구 로직이 있어 이 훅을 쓰지 않음.

## 판단 — createDraft 복구 vs accountId persist

`accountId`도 localStorage에 persist하고, 폐기 시 새 accountId를 저장하는 방식이 더 단순하지 않냐는 검토가 있었음. **createDraft 복구 방식을 선택.**

- **핵심 근거 — 초안은 공유 리소스:** [`DuesDraftAlert`](../../src/components/admin/dues/setup/components/DuesDraftAlert.tsx)가 **"(이전 작성자 : {name})"** 를 노출. 즉 한 초안을 **여러 관리자가 이어서 작성**할 수 있음(`createDraft` 응답의 `isNew` / `lastModifiedByName`가 이를 뒷받침).
- **persist 방식의 stale 리스크:**
  - 본인 폐기는 `reset()`이 localStorage까지 지우므로 문제없음.
  - 문제는 **다른 클라이언트(다른 관리자 / 다른 탭·기기)가 그 초안을 폐기·완료**하는 경우. 그 클라이언트의 `reset()`은 자기 localStorage만 지우므로, 이쪽 브라우저엔 죽은 accountId가 그대로 남음 → 새로고침 시 죽은/완료된 리소스를 타격해 화면이 깨짐. Step2~5엔 복구 로직이 없어 빠져나올 수 없음.
  - localStorage는 "이 브라우저가 마지막으로 본 값"일 뿐, 그 사이 서버가 바뀐 걸 알 수 없음.
- **createDraft 방식의 이점:**
  - 새로고침마다 서버 진실을 다시 가져오므로 **항상 살아있는 accountId를 보장**. 완료/폐기된 경우도 서버 응답으로 올바르게 반응.
  - store 주석이 명시한 원저자 의도(`새로고침/재접속 시 null 초기화 → 초안 생성 API 재호출`)와 **부합**. 이번 버그는 그 재호출을 Step1에만 구현하고 Step2~5에 빠뜨린 것 → 이번 수정이 원래 의도를 완성.
  - 비용은 새로고침 시 createDraft 1회 호출뿐(idempotent).
